# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Study POC for Azure Service Bus in C#/.NET 10, modeled on a life-insurance policy issuance domain ("Vida"). The goal is to explain Service Bus concepts by contrasting them with Kafka and RabbitMQ, which the user already knows. Code identifiers, comments, logs and docs are in **Portuguese (pt-BR)**. Keep that convention.

Work is split into phases (status table in `README.md`), each with code plus a study note in `docs/fase-N-*.md` (Kafka/RabbitMQ comparisons, Microsoft Learn links). Done: 1 queues, settlement, DLQ; 2 topic + filtered subscriptions; 3 sessions/dedup/scheduled/deferral; 4 REST API + outbox on SQL Server; 5 OpenTelemetry → App Insights + tests; 7 services per squad (event-driven, Bicep per owner, contracts as NuGet packages, inbox + outbox in the Subscrição). Phase 6 (Azure DevOps + Functions) was dropped by the user. The notes for phases 1–5 describe the code of their time (Producer/Consumer/Assinantes, queue `propostas`); `docs/fase-7-servicos-por-squad.md` describes the current shape, and `docs/plano-reestruturacao.md` records how it got there, stage by stage.

## Architecture

### Services and ownership

| Squad | Project (folder) | Port | Publishes | Subscribes / reads |
|---|---|---|---|---|
| Propostas | `src/Propostas/Vida.Propostas` (+ `Vida.Propostas.Contratos`) | 5180 | topic `proposta-recebida` (via outbox) | `status-aprovada`, `status-recusada` |
| Subscrição | `src/Subscricao/Vida.Subscricao` (+ `Vida.Subscricao.Contratos`) | 5181 | topics `apolice-emitida`, `proposta-recusada` (via outbox) | queue `subscricao-entrada` (fed by subscription `subscricao` with `forwardTo`), queue `endossos` |
| Cobrança | `src/Cobranca/Vida.Cobranca` | 5182 | — | `cobranca` |
| Notificação | `src/Notificacao/Vida.Notificacao` | 5183 | — | `notificacao`, `notificacao-recusa` |
| Resseguro | no service, on purpose | — | — | `alto-valor` (messages wait; the panel card counts them) |
| Plataforma | `src/Plataforma/*` + `src/Operacao/Vida.Operacao` | 5184 | — | discovers every entity (admin client) |

Rules the code follows: a command goes to a queue, an event to a topic; one publisher per event (demo endpoints live in the owner of what they publish); each service reads only its own database and learns about others through events; whoever consumes owns the subscription, Bicep included; the outbox lives inside the service whose state changes (copied, not shared). New subscriptions/topics go into that squad's Bicep module and into the owner's code, never into a global list.

### Projects and references

- **Inside a squad, `ProjectReference`; across squads, `PackageReference` with a version.** Shared packages: `Vida.Plataforma`, `Vida.LogsAoVivo`, `Vida.Telemetria` (Plataforma squad, 1.0.0), `Vida.Propostas.Contratos` (1.1.0; 1.0.0 also in the feed), `Vida.Subscricao.Contratos` (1.0.0, depends on the Propostas contracts package). Feed `vida` = folder `pacotes/` (gitignored), with package source mapping in `nuget.config` (`Vida.*` only from it). **A published version is immutable** (the global NuGet cache keys by version): to change a shared library, bump its `<Version>`, run `publicar-pacotes.ps1`, then bump the consumers that need it. `-Forcar` republishes the same version and clears the local cache entry, for local experiments only. `Vida.Operacao` uses `ProjectReference` to the platform libraries (same squad). In Propostas, its own contract resolves as project even though it also arrives as a package dependency.
- **Contracts expose their own addresses:** `MensagensProposta.Topico`/`Tipo`, `MensagensApolice.Topico`/`Tipo`, `MensagensRecusa.Topico`/`Tipo`, `MensagensEndosso.Fila`/`Tipo`. Application properties: `PropriedadesDaProposta` (`plano`, `simularFalha`, `retryComBackoff`, `tentativa`, `simularQuedaAposGravar`) and `PropriedadesDeRoteamento` (`plano`, `capitalSegurado`, `requerRevisao`, `prioridade`, `versao`). Each service declares the subscriptions it reads (`ProcessadorDeCobranca.Assinatura`, `ProcessadorDeDesfechos.AssinaturaAprovada`...). `subscricao-entrada` is internal to the Subscrição (`ProcessadorDePropostas.Fila`).
- **`Vida.Plataforma`:** `Conexao/ServiceBusClientFactory`; `Processamento/` (`ProcessadorControlavel` wraps a `ServiceBusProcessor` or `ServiceBusSessionProcessor`; `GerenciadorDeProcessadores` hosted service; `ProcessadoresController` `GET /processadores`, `POST /processadores/{nome}/iniciar|parar`; generic `AssinaturasController` `GET /assinaturas` listing the subscriptions of the app's own processors with filters and counts; registered by `AddProcessadoresControlaveis()`, each processor by `AddProcessadorControlavel(sp => x.CriarProcessador())`); `Mensagens/` (`SerializacaoDeContratos`, `LeituraDeContratos.Ler<T>` returns null on an unreadable body, `MotivosDeDeadLetter`); `Topologia/DescricaoDeRegras`; `Api/` (`ExtensoesDeValidacao.ProblemaDeValidacao`, `TratadorDeErrosDoServiceBus`).
- **`src/Directory.Build.props`:** links `servicebus.local.json` into every `Exe` output and `sqlserver.local.json` into projects with `<UsaSqlServerLocal>true</UsaSqlServerLocal>` (Propostas, Subscrição); apps load them from `AppContext.BaseDirectory`, so rebuild after `up.ps1`/`sql-up.ps1` create them. It also sets `GenerateMvcApplicationPartsAssemblyAttributes=false`: without it the SDK auto-registered the platform's controllers in every app (the Producer exposed a broken `/processadores`). Library controllers come in only through their `AddXxx()` (`AddApplicationPart`).
- The user prefers one class per file and folders named after what the code does. Follow that for new code. Same squad → same folder under `src/<Squad>/` and `tests/<Squad>/`.

### Conventions shared by the services

- **Every HTTP API is an MVC controller** (`[ApiController]` + attribute routes, in `Controllers/`). The user dislikes minimal APIs: don't add `app.MapGet`/`MapPost`/`MapGroup`. Request/response records go in `Contratos/` (demo ones in `Contratos/Demonstracao/`). The only `Map*` calls are `app.MapControllers()` and, inside `if (app.Environment.IsDevelopment())`, `app.MapOpenApi()` and `app.MapScalarApiReference()`. `iniciar.ps1` and `launchSettings.json` set `DOTNET_ENVIRONMENT=Development`. Projects with OpenAPI have `GenerateDocumentationFile` on (CS1591 suppressed). Production-ready endpoints are in `/openapi/v1.json` (Propostas: only `/api/propostas`; Operação: its tools); demonstration endpoints (they generate data or simulate failures for the panel) are under `/demo/`, in `Controllers/Demonstracao/`, tag "Demonstração", `[ApiExplorerSettings(GroupName = "demo")]`, contract `/openapi/demo.json`, logic in `Cenarios/`. An endpoint only a panel scenario needs is demonstration. Request bodies have `Validar()`; errors go through `this.ProblemaDeValidacao(erros)`.
- **All services are ASP.NET Core hosts with fixed ports** (`Urls` in each `appsettings.json`). `builder.AddLogsAoVivo()` keeps the last 500 log entries and streams them on `GET /logs` (SSE). Entries carry `PropostaId`/`ApoliceId`/`MessageId` from structured-log placeholders, which the panel uses to correlate lines across columns: use those placeholder names when logging business ids.
- **Config precedence:** each `Program.cs` re-adds environment variables and command line after the `*.local.json` files, so they win. Integration tests depend on this (`WebApplicationFactory` passes settings as command line).
- **Auth is Entra ID only:** the namespace has `disableLocalAuth: true`. `ServiceBusClientFactory` builds the `ServiceBusClient` with `DefaultAzureCredential` (locally `az login`) and exponential retry. Bicep grants the deploying user `Azure Service Bus Data Owner`; RBAC can take minutes to propagate (401 right after `up.ps1` is expected). The first connection takes ~20 s while `DefaultAzureCredential` walks its chain. One `ServiceBusClient` per app.
- **Contracts are read strictly** (`SerializacaoDeContratos.Leitura` / `LeituraDeContratos.Ler<T>`): required constructor params + nullable annotations; an unreadable body is dead-lettered with `PayloadInvalido`, never abandoned.
- **Subscription filters only see properties, never the body.** `MensagensApolice.Criar` copies routing fields (`plano`, `capitalSegurado` as `long`, `requerRevisao` as bool from the Subscrição's `Dominio/PoliticaDeRevisao`) into application properties. Correlation filters declared via ARM only match strings, so bool routing uses SQL filters. In Bicep, don't redefine `$Default` (the deploy succeeds but leaves no rules); give each rule its own name.
- **Telemetry (phase 5):** `builder.AddTelemetria("Vida.<Servico>")` after the local config files. Azure Monitor if `ApplicationInsights:ConnectionString` (needs `Credential = DefaultAzureCredential`, App Insights has `DisableLocalAuth`), OTLP if `OTEL_EXPORTER_OTLP_ENDPOINT`. Business spans via `FonteDeAtividades.Fonte`, metrics via `MetricasDeNegocio`. Polling and startup queries run inside `SuppressInstrumentationScope`; panel routes (`RotasDoPainel`: `/logs`, `/namespace`, `GET /assinaturas`, `GET /processadores`) are filtered and suppressed (the distro's sampler is not parent-based, so the filter alone leaked orphan child spans). Each outbox stores the current `Diagnostic-Id` with the row so the consumer continues the producing trace.
- **`System.Security.Cryptography.Pkcs` is pinned on purpose** in the Propostas and Subscrição csproj to override a vulnerable transitive version from `Microsoft.Data.SqlClient`. Don't remove it as unused.

### Flows

- **Proposal (Propostas):** `POST /api/propostas` (`Controllers/PropostasController`) adds `PropostaRegistrada` and a `MensagemDeSaida` (the `ServiceBusMessage` from `MensagensProposta.Criar`, serialized, destination `MensagensProposta.Topico`) in one `SaveChanges`, returning 201 + Location. `Outbox/DespachanteDoOutbox` polls every second inside a DB transaction (`UPDLOCK, READPAST, ROWLOCK`), sends, marks `PublicadaEm` and moves the proposal from `Recebida` to `EnviadaParaAnalise` (never overwriting an outcome); on `ServiceBusException` it backs off per row (max 10 s). `Idempotency-Key` maps to a filtered unique index (repeat → 200 + `Idempotent-Replayed`). `Desfechos/ProcessadorDeDesfechos` (only with SQL configured) reads `status-aprovada`/`status-recusada`; `RegistroDeDesfechos` sets `Aprovada` (+ `ApoliceId`) or `Recusada` (+ motive); repeats are no-ops, unknown proposals (demo endpoints) are ignored. Migrations at startup (`Dados/MigracaoDoBanco`, non-fatal: without SQL the API returns 503 via `TratadorDeErrosDoBanco`). Demos: `/demo/propostas` (+ `lote`, `invalida`, `sem-outbox`), `/demo/outbox` (state), `/demo/outbox/simulacao` (fake broker outage for the dispatcher).
- **Analysis (Subscrição, `Analise/ProcessadorDePropostas`):** processor on `subscricao-entrada`, PeekLock, `AutoCompleteMessages = false`, explicit settlement. Unreadable body → `DeadLetter(PayloadInvalido)`. `simularFalha` → `Abandon` (redelivers immediately, no backoff: an intended teaching point; after `maxDeliveryCount` 5 the broker dead-letters with `MaxDeliveryCountExceeded`). `simularFalha` + `retryComBackoff` → Complete + send a copy to the **same queue** with `ScheduledEnqueueTime` (2^n s) and `tentativa + 1` in one transaction (single entity, so no `EnableCrossEntityTransactions`); recovers at attempt 3, attempt 5 dead-letters with `TentativasEsgotadas`. Age > 80 → recusa; otherwise approve with `CalculadoraDePremio`/`PoliticaDeRevisao` (internal `Dominio/`). Both outcomes go through `RegistroDaAnalise`: one `SaveChanges` with the inbox row (`MessageId` as primary key; a duplicate-key error means another instance won), the business row (`Apolices`/`Recusas`) and the outbox row; only after the commit the message is completed. A redelivery already in the inbox is completed without writing or publishing. `simularQuedaAposGravar` abandons after the commit on the first delivery to show it. `Outbox/` (copy of Propostas' pattern) publishes. A business rejection is an outcome, not a failure: never dead-letter it. Without the `Subscricao` connection string, the `propostas` processor doesn't start (proposals wait in the queue).
- **Endorsements (Subscrição, `Endossos/ProcessadorDeEndossos`):** queue `endossos` has `requiresSession` and `requiresDuplicateDetection` (creation-time only). `MensagensEndosso.Criar` sets `SessionId = ApoliceId`, `MessageId = "{apoliceId}/v{versao}"`. Session state (`EstadoDaSessao`: last applied version + deferred version → `SequenceNumber`): already applied → Complete; ahead → save state, then Defer; next → apply, save state, Complete, then fetch due deferred ones (`ReceiveDeferredMessagesAsync`). State is saved before Complete/Defer because session state is not transactional. Demos `/demo/endossos/*` and `/demo/apolices` live here (the Subscrição owns those entities); `/demo/apolices` publishes an invented `ApoliceEmitida` to test only the filters.
- **Subscribers (Cobrança, Notificação):** one processor class per subscription on `ProcessadorControlavel`; their own `GET /assinaturas` shows filters and pending counts. Logs start with `[assinatura]`, which the panel turns into a badge.
- **Operations (`Vida.Operacao/Ferramentas`):** `DescobertaDeEntidades` lists queues, topics and subscriptions (with counts and `forwardTo`) on every call; no squad contract referenced. `GET /filas`, `GET /filas/{nome}/mensagens?dlq=`, `POST /filas/{nome}/dlq/reprocessar?removerPropriedade=`, `GET /assinaturas`, `GET /assinaturas/regras`, `GET /assinaturas/{nome}/mensagens?dlq=`, `GET /namespace`. Peek shows Subject, properties and the start of the body as text; it refuses a subscription with `forwardTo` (the broker allows no receiver on a forward source) and a session queue, explaining why. `ReprocessamentoDaDlq` skips permanent reasons and only takes messages up to the DLQ's max `SequenceNumber` peeked at the start; it sends the copy before completing the DLQ message (duplicates rather than loses). A failed forward lands in the source's transfer DLQ (`.../$Transfer/$DeadLetterQueue`), not in the destination's DLQ.
- **Infra (`infra/main.bicep` → `infra/servicos/`):** `plataforma.bicep` (namespace, RBAC, App Insights); `<servico>.publica.bicep` creates the topics/queues the service owns and outputs their names; `<servico>.assina.bicep` receives those names as parameters (which orders the deploy and breaks the Propostas ↔ Subscrição cycle) and creates its subscriptions; `padroes.bicep` exports `propriedadesDeAssinatura(lockDuration)`. `up.ps1` parameters and outputs did not change.

### Panel (`web/painel`, Vite + React + TS)

`src/apps.ts` is the single list of services (id, name, port, color, role, folder): the `App` type, columns, tabs, error messages and the Vite proxy (`vite.config.ts` imports it, hence `allowImportingTsExtensions`) come from it. A new service needs an entry there, in the `$apps` array of `iniciar.ps1` and in `.vscode/launch.json`. Scenario dropdown (catalog in `src/cenarios.ts`, each call goes to the endpoint's owner), one live log column per service (the "Colunas" bar hides columns in `localStorage`; hidden ones stay connected and in the trail), the "Resseguro (sem serviço)" card (pending count of `alto-valor`, from the Operação), on/off controls (processors in the Subscrição column, subscriptions in Cobrança/Notificação), and the id trail (`correlacao.ts`: lines link by business ids; lines without ids join through the TraceId of trail lines, but the TraceId never pulls lines that have ids, because one trace can carry many messages). Each line gets a component badge from its logger category (`src/origens.ts`) and a trace control (Aspire Dashboard when up, detected through `/api/aspire`; otherwise copies the TraceId). A new demo endpoint needs an entry in `cenarios.ts`; a new logging class, one in `origens.ts`.

### Tests

Per squad: `tests/Plataforma/Vida.Plataforma.Testes` (Operação tools), `tests/Propostas/Vida.Propostas.Testes` (API contracts, outbox message, the published contract, strict reading), `tests/Propostas/Vida.Propostas.Testes.Integracao` (`FabricaDaApi` = Propostas in memory + Testcontainers SQL Server, dispatcher and outcome processor removed from the host; `ServiceBusFalso` subclasses `ServiceBusClient`/`ServiceBusSender`; `Banco` collection, sequential), `tests/Subscricao/Vida.Subscricao.Testes` (pricing, review policy, endorsement decision, its contract), `tests/Subscricao/Vida.Subscricao.Testes.Integracao` (`RegistroDaAnalise` against Testcontainers SQL Server: inbox, redelivery, rejection). Extract decisions out of handlers (like `DecisaoDeEndosso`, `RegistroDaAnalise`) to test them. Pass `TestContext.Current.CancellationToken` to async calls (xUnit1051).

## Working with the user

- Talk to the user in Portuguese. They read the code closely, ask concept questions as they go, and add XML doc comments themselves. Keep their edits.
- Commit only when asked, directly on `master`, with no branches. Before committing, check for and mention the user's own uncommitted edits.
- Infra costs money while it exists. At the end of a session, or after a deploy the user didn't ask to keep, remind them to run `down.ps1`. Check with `az group exists -n rg-servicebus-poc`.
- The `!` prompt prefix runs **bash**, which eats backslashes. Suggest `! pwsh -File infra/up.ps1` (or `down.ps1`, `-ModoDebug`), not `.\infra\up.ps1`.
- Before writing Service Bus facts into docs (limits, semantics), verify them with the Azure MCP `documentation` tool. One claim about multiple matching rules was wrong until checked.

## Conventions for new phases

- Follow the Azure best-practice choices already made: managed identity/RBAC instead of keys, one `ServiceBusClient` singleton per app, infrastructure in Bicep rather than portal clicks, latest stable SDKs (`Azure.Messaging.ServiceBus`, `Azure.Identity`).
- Keep cost in mind: stay on the Standard tier (Premium is ~US$0.93/h). For anything stateful that isn't Service Bus, such as SQL Server for the outbox, run it locally in Docker (`infra/sql-up.ps1`), one database per service.
- A change to a shared library or contract is a new package version (bump `<Version>`, `publicar-pacotes.ps1`), not an edit consumers pick up silently.
- When finishing a phase, update the status table in `README.md` and add `docs/fase-N-*.md` in the same style as `docs/fase-1-filas.md`.
