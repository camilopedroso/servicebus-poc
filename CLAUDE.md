# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Study POC for Azure Service Bus in C#/.NET 10, modeled on a life-insurance policy issuance domain ("Vida"). The goal is to explain Service Bus concepts by contrasting them with Kafka and RabbitMQ, which the user already knows. Code identifiers, comments, logs and docs are in **Portuguese (pt-BR)**. Keep that convention.

The work is split into phases (roadmap and status in `README.md`). Each phase gets code plus a study note in `docs/fase-N-*.md` with Kafka/RabbitMQ comparisons, and Microsoft Learn links. Done: 1 queues, settlement, DLQ; 2 topic + subscriptions with filters, cross-entity transaction; 3 sessions/dedup/scheduled/deferral; 4 REST API + Outbox on SQL Server; 5 OpenTelemetry → App Insights + tests. Phase 6 (Azure DevOps + Functions) was dropped by the user; the POC is complete.

## Architecture

- **Config flow:** `infra/up.ps1` deploys `main.bicep` and writes the namespace FQDN (and, since phase 5, `ApplicationInsights:ConnectionString`) to `src/servicebus.local.json` (gitignored). The apps link that file into their output via a csproj `<None ... Condition="Exists(...)">` item and load it from `AppContext.BaseDirectory`. If the build ran before `up.ps1`, the file isn't copied, so rebuild after running it.
- **Auth is Entra ID only:** the namespace has `disableLocalAuth: true`, so SAS keys and connection strings will not work. `ServiceBusClientFactory` (in `Vida.Mensageria/Conexao/`) builds the single `ServiceBusClient` with `DefaultAzureCredential` (locally that's `az login`) and exponential retry. Bicep grants the deploying user `Azure Service Bus Data Owner`. RBAC can take minutes to propagate, so 401s right after `up.ps1` are expected. The first consumer connection takes ~20 s while `DefaultAzureCredential` walks its credential chain.
- **`Vida.Mensageria`:** organized by role, one class per file, namespace = `Vida.Mensageria.<Pasta>`:
  - `Contratos/`: message payloads (`PropostaSeguroVida`, `ApoliceEmitida`, `PropostaRecusada`)
  - `Topologia/`: broker entity names (`Filas`, `Topicos`, `Assinaturas` with `TopicoDe(nome)`, since subscriptions span two topics) and `DescricaoDeRegras` (rule → text). New queues, topics and subscriptions must be added both here and in `infra/main.bicep`.
  - `Mensagens/`: how messages are built (`MensagensApolice`, `MensagensRecusa`, application-property names in `Propriedades`, `TiposDeMensagem`, `MotivosDeDeadLetter`)
  - `Conexao/`: `ServiceBusClientFactory`
  - `Dominio/`: business rules that aren't messaging (`CalculadoraDePremio`, `Planos`)
- The user prefers one class per file and folders named after what the code does. Follow that for new code.
- **Every HTTP API is an MVC controller** (`[ApiController]` + attribute routes, in a `Controllers/` folder). The user dislikes minimal APIs: don't add `app.MapGet`/`MapPost`/`MapGroup`. Request/response records go in `Contratos/`. The only `Map*` calls left are `app.MapControllers()` and the framework's `app.MapOpenApi()`.
- **`Vida.Consumer` (`Worker.cs`):** a `BackgroundService` around `ServiceBusProcessor` in PeekLock mode with `AutoCompleteMessages = false`. Settlement is explicit and demonstrates the distinct DLQ paths:
  - unreadable body → `DeadLetter(MotivosDeDeadLetter.PayloadInvalido)`
  - application property `simularFalha=true` → `Abandon`. The broker dead-letters it after the queue's `maxDeliveryCount` (5) with reason `MaxDeliveryCountExceeded`.
  - age > 80 → `Complete` + send `PropostaRecusada` to topic `proposta-recusada` in one transaction (subscription `notificacao-recusa` notifies the client). A business rejection is an outcome, not a failure, so it must not be dead-lettered: that left the client un-notified and made DLQ resubmission loop.
  - otherwise → `Complete` + send `ApoliceEmitida`
  - Note that `Abandon` redelivers immediately with no backoff. This is an intended teaching point.
- **Phase 2 flow:** on the happy path, `Vida.Consumer` completes the queue message and sends `ApoliceEmitida` to topic `apolice-emitida` inside one `TransactionScope`. This needs `EnableCrossEntityTransactions` on its client (`ServiceBusClientFactory.Criar(..., transacoesEntreEntidades: true)`), the sender created from that same client, and Complete as the first operation so the queue is the "via" entity. In `Vida.Assinantes`, `GerenciadorDeAssinaturas` (hosted service) owns one `ProcessadorDeAssinatura` per subscription, all sharing one client. Each processor can be started/stopped at runtime (`POST /assinaturas/{nome}/iniciar|parar`, in `Controllers/AssinaturasController`). `GET /assinaturas` returns pending/DLQ counts via `ServiceBusAdministrationClient`.
- **Subscription filters only see properties, never the body.** `MensagensApolice.Criar` copies routing fields (`plano`, `capitalSegurado` as `long`, `requerRevisao` as bool from `Dominio/PoliticaDeRevisao`) into application properties. Correlation filters declared via ARM only match string values, so bool routing uses SQL filters. Change those together with the Bicep rules. In Bicep, don't redefine the `$Default` rule: the deploy succeeds but leaves the subscription with no rules. Give each rule its own name.
- **All three apps are ASP.NET Core hosts with fixed ports** (`Urls` in each `appsettings.json`). `Vida.LogsAoVivo` adds a logger provider (`builder.AddLogsAoVivo()`) that keeps the last 500 entries and streams them on `GET /logs` as Server-Sent Events (`LogsController`, registered as an application part by `AddLogsAoVivo()`, so every app must call `app.MapControllers()`). Entries carry `PropostaId`/`ApoliceId`/`MessageId` taken from structured-log placeholders, which the panel uses to correlate lines across columns. Use those placeholder names when logging business ids.
- **`web/painel`** (Vite + React + TS): a scenario dropdown (catalog in `src/cenarios.ts`) that calls the Producer, three live log columns, a subscription on/off control in the Assinantes column, and an id "trail" that highlights one message across all three processes. Columns are processes; inside a column, each line gets a component badge from its logger category (`src/origens.ts`: API, outbox, cenário, propostas, endossos...) and a "trace" control (opens the trace in the Aspire Dashboard when it is up, detected through the Vite proxy `/api/aspire`; otherwise copies the TraceId for App Insights search). The trail (`correlacao.ts`) links lines by business ids; lines without ids join through the TraceId of trail lines, but the TraceId never pulls lines that have ids, because one trace can carry many messages (a batch POST, an outbox batch). A new Producer endpoint needs a matching entry in `cenarios.ts`; a new logging class needs an entry in `origens.ts`.
- **Phase 3 flow:** queue `endossos` has `requiresSession` and `requiresDuplicateDetection`, which can only be set at creation (that is why it is a new queue, not `propostas`). `MensagensEndosso.Criar` sets `SessionId = ApoliceId` and `MessageId = "{apoliceId}/v{versao}"` (stable across resends, so dedup works). `Vida.Consumer/Endossos/ProcessadorDeEndossos` is a `ServiceBusSessionProcessor` that keeps `EstadoDaSessao` (last applied version + deferred version → `SequenceNumber`) in session state: already applied → Complete; ahead → save state, then Defer; next → apply, save state, Complete, then fetch due deferred ones via `args.GetReceiveActions().ReceiveDeferredMessagesAsync`. State is always saved before Complete/Defer because session state is not transactional.
- **The cross-entity-transaction client is exclusive.** With `EnableCrossEntityTransactions`, every link of that client is routed through the first entity it touched, so a receiver on another queue fails with "Local transactions cannot span multiple top-level entities". `ProcessadorDeEndossos` therefore uses its own keyed `ServiceBusClient` (`ProcessadorDeEndossos.ChaveDoClient`). Any new processor in `Vida.Consumer` on a different entity needs the same.
- **Retry with backoff (phase 3):** with `simularFalha` + `retryComBackoff`, `Worker` completes the message and sends a copy with `ScheduledEnqueueTime` (2^n s) and `tentativa + 1` in one transaction; the simulated dependency recovers at attempt 3, and attempt 5 dead-letters with `TentativasEsgotadas` (not permanent, so resubmit takes it).
- **Contracts are read strictly:** `SerializacaoDeContratos.Leitura` (required constructor params + nullable annotations). Without it `{}` deserializes into an all-default record and was being approved. Use it whenever a consumer reads a body.
- **Phase 4 flow (outbox):** `POST /api/propostas` (`Controllers/PropostasController`) adds `PropostaRegistrada` and a `MensagemDeSaida` (the `ServiceBusMessage` from `MensagensProposta.Criar`, serialized) in one `SaveChanges`, returning 201 + Location without touching Service Bus. `Outbox/DespachanteDoOutbox` polls every second inside a DB transaction (`UPDLOCK, READPAST, ROWLOCK`), sends the batch, marks `PublicadaEm` and sets the proposal to `EnviadaParaAnalise`; on `ServiceBusException` it backs off per row (`ProximaTentativaEm`, max 10 s). `Idempotency-Key` maps to a filtered unique index; a repeat returns 200 + `Idempotent-Replayed`. `POST /demo/outbox/simulacao` fakes a broker outage for the dispatcher only; `POST /demo/propostas/sem-outbox` demonstrates the dual-write failure. The outcome comes back as events: `Desfechos/ProcessadorDeDesfechos` (hosted service, registered only when SQL is configured) listens to subscriptions `status-aprovada` (topic `apolice-emitida`) and `status-recusada` (topic `proposta-recusada`) and `RegistroDeDesfechos` sets `Aprovada` (+ `ApoliceId`) or `Recusada` (+ `MotivoDaRecusa`); a repeated event is a no-op, and events for proposals not in the DB (demo endpoints) are ignored. The dispatcher only moves a proposal out of `Recebida`, so an outcome that arrives before it marks the row is not overwritten. `Assinaturas.DoAssinantes` are the subscriptions `Vida.Assinantes` processes, `DoProducer` the Producer ones; `Todas` (both) is for peek and rule listing. Migrations run at startup (`Dados/MigracaoDoBanco`, non-fatal: without SQL the API returns 503 via `TratadorDeErros`, phases 1–3 keep working). `src/sqlserver.local.json` is linked into the Producer output like `servicebus.local.json`, so rebuild after the first `sql-up.ps1`.
- **`System.Security.Cryptography.Pkcs` is pinned on purpose** in `Vida.Producer.csproj` to override a vulnerable transitive version from `Microsoft.Data.SqlClient`. Don't remove it as unused.
- **Phase 5 (telemetry):** `Vida.Telemetria.AddTelemetria(builder, "Vida.<App>")` wires the Microsoft OpenTelemetry Distro in all three apps, after the local config files are loaded. Exporters are set explicitly from config: Azure Monitor if `ApplicationInsights:ConnectionString` (written by `up.ps1` into `servicebus.local.json`; App Insights has `DisableLocalAuth`, so it needs `Credential = DefaultAzureCredential`), OTLP if `OTEL_EXPORTER_OTLP_ENDPOINT`; with neither, telemetry is off. Business spans go through `FonteDeAtividades.Fonte`, metrics through `MetricasDeNegocio`. Keep noise out of traces: polling and startup queries run inside `SuppressInstrumentationScope`, and panel routes (`RotasDoPainel`: `/logs`, `/namespace`, `GET /assinaturas`) are both filtered in the ASP.NET Core instrumentation and run inside `SuppressInstrumentationScope` (`SupressaoNasRotasDoPainel`); the filter alone let child spans through, orphaned, because the distro's sampler is not parent-based. `MensagemDeSaida.De` stores the current `Diagnostic-Id` with the outbox row so the consumer continues the POST's trace, not the dispatcher's.
- **Config precedence:** each `Program.cs` re-adds environment variables and command line after the `*.local.json` files, so they win. Integration tests depend on this (`WebApplicationFactory` passes its settings as command line). Keep that order when adding config files.
- **Tests:** `tests/Vida.Testes.Unidade` (pure logic; extract decisions out of handlers, like `DecisaoDeEndosso`, to test them) and `tests/Vida.Testes.Integracao` (`FabricaDaApi` = Producer in memory + Testcontainers SQL Server, dispatcher removed from the host; `ServiceBusFalso` subclasses `ServiceBusClient`/`ServiceBusSender`). Integration tests share one container in the `Banco` collection and run sequentially.
- **DLQ resubmit (`ReprocessamentoDaDlq`)** skips permanent reasons (`MotivosDeDeadLetter.Permanentes`) and only takes messages up to the DLQ's max `SequenceNumber` peeked at the start, so a copy that dies again can't loop.
- **`Vida.Producer`:** MVC controllers in `Controllers/` (`[ApiController]` + attribute routes; no CLI args). Validation errors from `Validar()` go through `this.ProblemaDeValidacao(erros)`; scoped `BancoDePropostas` is taken by `[FromServices]` in actions that need it, not by constructors, so controllers without DB keep working when SQL is not configured. A new logging controller needs its class name in `origens.ts`. Endpoints are split into production-ready and demonstration. Production-ready: `/api/propostas` and the operations tools (`/filas`, `/assinaturas`, `GET /outbox`), in `Controllers/`, contract `/openapi/v1.json`. Demonstration (they generate test data, sorting null fields, or simulate failures for the panel scenarios): `Controllers/Demonstracao/`, routes under `/demo/`, tag "Demonstração", `[ApiExplorerSettings(GroupName = "demo")]` so they only appear in `/openapi/demo.json`; their bodies are in `Contratos/Demonstracao/` and their logic in `Cenarios/` (`EnvioDePropostas`, `PublicacaoDeApolices`, `EnvioDeEndossos`, `EnvioSemOutbox`). The panel decides which is which: an endpoint only a scenario needs is demonstration. Operations logic lives in `Operacao/` (`InspecaoDeEntidades`, `ReprocessamentoDaDlq`). Request bodies have a `Validar()` method, and `Erros/TratadorDeErros` turns `ServiceBusException`/auth errors into ProblemDetails. It sets `MessageId` to the business id (groundwork for duplicate detection in phase 3), `Subject` to the event type (for subscription filters in phase 2), and `CorrelationId` to the client id. It also hosts the operations tools: peek, DLQ peek, and DLQ resubmit. Resubmit sends the copy before completing the DLQ message, so a failure duplicates rather than loses (at-least-once).

## Working with the user

- Talk to the user in Portuguese. They read the code closely, ask concept questions as they go, and add XML doc comments themselves. Keep their edits.
- Commit only when asked, directly on `master`, with no branches. Before committing, check for and mention the user's own uncommitted edits.
- Infra costs money while it exists. At the end of a session, or after a deploy the user didn't ask to keep, remind them to run `down.ps1`. Check with `az group exists -n rg-servicebus-poc`.
- The `!` prompt prefix runs **bash**, which eats backslashes. Suggest `! pwsh -File infra/up.ps1` (or `down.ps1`, `-ModoDebug`), not `.\infra\up.ps1`.
- Before writing Service Bus facts into docs (limits, semantics), verify them with the Azure MCP `documentation` tool. One claim about multiple matching rules was wrong until checked.

## Conventions for new phases

- Follow the Azure best-practice choices already made: managed identity/RBAC instead of keys, one `ServiceBusClient` singleton per app, infrastructure in Bicep rather than portal clicks, latest stable SDKs (`Azure.Messaging.ServiceBus`, `Azure.Identity`).
- Keep cost in mind: stay on the Standard tier (Premium is ~US$0.93/h). For anything stateful that isn't Service Bus, such as SQL Server for the outbox, run it locally in Docker (`infra/sql-up.ps1`).
- When finishing a phase, update the status table in `README.md` and add `docs/fase-N-*.md` in the same style as `docs/fase-1-filas.md`.
