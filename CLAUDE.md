# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Study POC for Azure Service Bus in C#/.NET 10, modeled on a life-insurance policy issuance domain ("Vida"). The goal is to explain Service Bus concepts by contrasting them with Kafka and RabbitMQ, which the user already knows. Code identifiers, comments, logs and docs are in **Portuguese (pt-BR)**. Keep that convention.

Work was done in phases (status table in `README.md`). The docs are consolidated: `docs/como-funciona.md` is the single explanation of the current system (Mermaid diagrams, Kafka/RabbitMQ comparison, guarantees, a "stop X, call Y, observe Z" test script, limits, Microsoft Learn links). The per-phase notes were deleted (they live in git history). Done: 1 queues, settlement, DLQ; 2 topic + filtered subscriptions; 3 sessions/dedup/scheduled/deferral; 4 REST API + outbox on SQL Server; 5 OpenTelemetry → App Insights + tests; 7 services per squad (event-driven, Bicep per owner, contracts as NuGet packages, inbox + outbox in the Subscrição); 8 no demonstrations (production-like: backoff triggered by real transient failures, endorsement API, fail fast without DB, no panel). Phase 6 (Azure DevOps + Functions) was dropped by the user. There are no demo endpoints or simulations any more: don't reintroduce them; exercise failures through tests or by stopping the real dependency.

## Architecture

### Services and ownership

| Squad | Project (folder) | Port | Publishes | Subscribes / reads |
|---|---|---|---|---|
| Propostas | `src/Propostas/Vida.Propostas` (+ `Vida.Propostas.Contratos`) | 5180 | topic `proposta-recebida` (via outbox) | `status-aprovada`, `status-recusada` |
| Subscrição | `src/Subscricao/Vida.Subscricao` (+ `Vida.Subscricao.Contratos`) | 5181 | topics `apolice-emitida`, `proposta-recusada`; command to queue `endossos` from its own API (all via outbox) | queue `subscricao-entrada` (fed by subscription `subscricao` with `forwardTo`), queue `endossos` |
| Cobrança | `src/Cobranca/Vida.Cobranca` | 5182 | — | `cobranca` |
| Notificação | `src/Notificacao/Vida.Notificacao` | 5183 | — | `notificacao`, `notificacao-recusa` |
| Resseguro | no service, on purpose | — | — | `alto-valor` (messages wait; `GET :5184/assinaturas` counts them) |
| Plataforma | `src/Plataforma/*` + `src/Operacao/Vida.Operacao` | 5184 | — | discovers every entity (admin client) |

Rules the code follows: a command goes to a queue, an event to a topic; one publisher per event; each service reads only its own database and learns about others through events; whoever consumes owns the subscription, Bicep included; the outbox lives inside the service whose state changes (copied, not shared). New subscriptions/topics go into that squad's Bicep module and into the owner's code, never into a global list.

### Projects and references

- **Inside a squad, `ProjectReference`; across squads, `PackageReference` with a version.** Shared packages: `Vida.Plataforma` (1.0.1), `Vida.Telemetria` (1.1.0) (Plataforma squad), `Vida.Propostas.Contratos` (2.0.0: only `plano`, no simulation properties; older versions stay in the feed), `Vida.Subscricao.Contratos` (1.0.1, depends on the Propostas contracts package). `Vida.LogsAoVivo` was deleted in phase 8. Feed `vida` = folder `pacotes/` (gitignored), with package source mapping in `nuget.config` (`Vida.*` only from it). **A published version is immutable** (the global NuGet cache keys by version): to change a shared library, bump its `<Version>`, run `publicar-pacotes.ps1`, then bump the consumers that need it. `-Forcar` republishes the same version and clears the local cache entry, for local experiments only. `Vida.Operacao` uses `ProjectReference` to the platform libraries (same squad). In Propostas, its own contract resolves as project even though it also arrives as a package dependency.
- **Contracts expose their own addresses:** `MensagensProposta.Topico`/`Tipo`, `MensagensApolice.Topico`/`Tipo`, `MensagensRecusa.Topico`/`Tipo`, `MensagensEndosso.Fila`/`Tipo`. Application properties: `PropriedadesDaProposta` (`plano`), `PropriedadesDeRoteamento` (`plano`, `capitalSegurado`, `requerRevisao`, `prioridade`, `versao`). Each service declares the subscriptions it reads (`ProcessadorDeCobranca.Assinatura`, `ProcessadorDeDesfechos.AssinaturaAprovada`...). `subscricao-entrada` is internal to the Subscrição (`ProcessadorDePropostas.Fila`), and so is its retry counter property `tentativa` (`Analise/PropriedadesDaRetentativa`).
- **`Vida.Plataforma`:** `Conexao/ServiceBusClientFactory`; `Processamento/` (`ProcessadorControlavel` wraps a `ServiceBusProcessor` or `ServiceBusSessionProcessor`; `GerenciadorDeProcessadores` hosted service; `ProcessadoresController` `GET /processadores`, `POST /processadores/{nome}/iniciar|parar`; generic `AssinaturasController` `GET /assinaturas` listing the subscriptions of the app's own processors with filters and counts; registered by `AddProcessadoresControlaveis()`, each processor by `AddProcessadorControlavel(sp => x.CriarProcessador())`); `Mensagens/` (`SerializacaoDeContratos`, `LeituraDeContratos.Ler<T>` returns null on an unreadable body, `MotivosDeDeadLetter`); `Topologia/DescricaoDeRegras`; `Api/` (`ExtensoesDeValidacao.ProblemaDeValidacao`, `TratadorDeErrosDoServiceBus`).
- **`src/Directory.Build.props`:** links `servicebus.local.json` into every `Exe` output and `sqlserver.local.json` into projects with `<UsaSqlServerLocal>true</UsaSqlServerLocal>` (Propostas, Subscrição); apps load them from `AppContext.BaseDirectory`, so rebuild after `up.ps1`/`sql-up.ps1` create them. It also sets `GenerateMvcApplicationPartsAssemblyAttributes=false`: without it the SDK auto-registered the platform's controllers in every app (the Producer exposed a broken `/processadores`). Library controllers come in only through their `AddXxx()` (`AddApplicationPart`).
- The user prefers one class per file and folders named after what the code does. Follow that for new code. Same squad → same folder under `src/<Squad>/` and `tests/<Squad>/`.

### Conventions shared by the services

- **Every HTTP API is an MVC controller** (`[ApiController]` + attribute routes, in `Controllers/`). The user dislikes minimal APIs: don't add `app.MapGet`/`MapPost`/`MapGroup`. Request/response records go in `Contratos/`. The only `Map*` calls are `app.MapControllers()` and, inside `if (app.Environment.IsDevelopment())`, `app.MapOpenApi()` and `app.MapScalarApiReference()`. `iniciar.ps1` and `launchSettings.json` set `DOTNET_ENVIRONMENT=Development`. Projects with OpenAPI have `GenerateDocumentationFile` on (CS1591 suppressed). One document per API, `/openapi/v1.json` (Propostas: `/api/propostas`; Subscrição: `/api/apolices`; Operação: its tools). No demonstration endpoints. Request bodies have `Validar()`; errors go through `this.ProblemaDeValidacao(erros)`. POSTs that create take an optional `Idempotency-Key` (filtered unique index; repeat → 200 + `Idempotent-Replayed`).
- **All services are ASP.NET Core hosts with fixed ports** (`Urls` in each `appsettings.json`). Logs go to the console and, through OpenTelemetry, to App Insights/Aspire. When logging business ids, use the placeholders `PropostaId`/`ApoliceId`/`MessageId`: they become searchable attributes.
- **Config precedence:** each `Program.cs` re-adds environment variables and command line after the `*.local.json` files, so they win. Integration tests depend on this (`WebApplicationFactory` passes settings as command line).
- **Auth is Entra ID only:** the namespace has `disableLocalAuth: true`. `ServiceBusClientFactory` builds the `ServiceBusClient` with `DefaultAzureCredential` (locally `az login`) and exponential retry. Bicep grants the deploying user `Azure Service Bus Data Owner`; RBAC can take minutes to propagate (401 right after `up.ps1` is expected). The first connection takes ~20 s while `DefaultAzureCredential` walks its chain. One `ServiceBusClient` per app.
- **Contracts are read strictly** (`SerializacaoDeContratos.Leitura` / `LeituraDeContratos.Ler<T>`): required constructor params + nullable annotations; an unreadable body is dead-lettered with `PayloadInvalido`, never abandoned.
- **Subscription filters only see properties, never the body.** `MensagensApolice.Criar` copies routing fields (`plano`, `capitalSegurado` as `long`, `requerRevisao` as bool from the Subscrição's `Dominio/PoliticaDeRevisao`) into application properties. Correlation filters declared via ARM only match strings, so bool routing uses SQL filters. In Bicep, don't redefine `$Default` (the deploy succeeds but leaves no rules); give each rule its own name.
- **Telemetry (phase 5):** `builder.AddTelemetria("Vida.<Servico>")` after the local config files. Azure Monitor if `ApplicationInsights:ConnectionString` (needs `Credential = DefaultAzureCredential`, App Insights has `DisableLocalAuth`), OTLP if `OTEL_EXPORTER_OTLP_ENDPOINT`. Business spans via `FonteDeAtividades.Fonte`, metrics via `MetricasDeNegocio`. Polling and startup queries run inside `SuppressInstrumentationScope`. Each outbox stores the current `Diagnostic-Id` with the row so the consumer continues the producing trace. (Until 1.0.0, `Vida.Telemetria` also filtered the panel's polling routes; that went away with the panel.)
- **`System.Security.Cryptography.Pkcs` is pinned on purpose** in the Propostas and Subscrição csproj to override a vulnerable transitive version from `Microsoft.Data.SqlClient`. Don't remove it as unused.

### Flows

- **Proposal (Propostas):** `POST /api/propostas` (`Controllers/PropostasController`) adds `PropostaRegistrada` and a `MensagemDeSaida` (the `ServiceBusMessage` from `MensagensProposta.Criar`, serialized, destination `MensagensProposta.Topico`) in one `SaveChanges`, returning 201 + Location. `Outbox/DespachanteDoOutbox` polls every second inside a DB transaction (`UPDLOCK, READPAST, ROWLOCK`), sends, marks `PublicadaEm` and moves the proposal from `Recebida` to `EnviadaParaAnalise` (never overwriting an outcome); on `ServiceBusException` it backs off per row (max 10 s). `Desfechos/ProcessadorDeDesfechos` reads `status-aprovada`/`status-recusada`; `RegistroDeDesfechos` sets `Aprovada` (+ `ApoliceId`) or `Recusada` (+ motive); repeats are no-ops; an outcome for a proposal not in the database is an inconsistency and is dead-lettered with `PropostaDesconhecida`. Migrations at startup (`Dados/MigracaoDoBanco`, 10 attempts, then the host stops). Fail fast: without the `Propostas` connection string, `Program.cs` throws. A SQL outage during a request → 503 via `TratadorDeErrosDoBanco` (generic detail, exception only in the log).
- **Analysis (Subscrição, `Analise/ProcessadorDePropostas`):** processor on `subscricao-entrada`, PeekLock, `AutoCompleteMessages = false`, explicit settlement. Unreadable body → `DeadLetter(PayloadInvalido)`. Age > 80 → recusa; otherwise approve with `CalculadoraDePremio`/`PoliticaDeRevisao` (internal `Dominio/`). Both outcomes go through `RegistroDaAnalise`: one `SaveChanges` with the inbox row (`MessageId` as primary key; a duplicate-key error means another instance won), the business row (`Apolices`/`Recusas`) and the outbox row; only after the commit the message is completed. A redelivery already in the inbox is completed without writing or publishing. If writing throws a transient failure (`Analise/FalhasTransitorias`: SQL error numbers for timeout, connection, deadlock, Azure SQL throttling; `TimeoutException`), it completes and sends a copy to the **same queue** with `ScheduledEnqueueTime` (2^n s) and `tentativa + 1` in one broker transaction (single entity, so no `EnableCrossEntityTransactions`); attempt 5 dead-letters with `TentativasEsgotadas`. Any other exception propagates: the SDK abandons and `maxDeliveryCount` (5) dead-letters with `MaxDeliveryCountExceeded`. `Outbox/` (copy of Propostas' pattern) publishes. A business rejection is an outcome, not a failure: never dead-letter it. Fail fast without the `Subscricao` connection string, as in Propostas.
- **Endorsements (Subscrição):** `Controllers/ApolicesController`: `GET /api/apolices/{id}` (policy, `VersaoDosEndossos`, endorsements) and `POST /api/apolices/{id}/endossos` (`NovoEndosso { Tipo }`, optional `Idempotency-Key` per policy, 404 for an unknown policy, 202 + Location). `Endossos/RegistroDeEndossos.SolicitarAsync` computes max + 1 for the policy and writes `EndossoRegistrado` (PK `ApoliceId + Versao`; a duplicate key recomputes, up to 3 tries) plus the `EndossoSolicitado` command in the outbox in one `SaveChanges`. The outbox row stores `SessionId`, and the dispatcher groups sends by `(Destino, SessionId)` because a batch to a session entity must share one `SessionId`. Queue `endossos` has `requiresSession` and `requiresDuplicateDetection` (creation-time only). `MensagensEndosso.Criar` sets `SessionId = ApoliceId`, `MessageId = "{apoliceId}/v{versao}"`. `Endossos/ProcessadorDeEndossos` uses session state (`EstadoDaSessao`: last applied version + deferred version → `SequenceNumber`): already applied → Complete; ahead → save state, then Defer; next → apply, save state, Complete, then fetch due deferred ones (`ReceiveDeferredMessagesAsync`). Apply = `RegistroDeEndossos.AplicarAsync`: `UPDATE Apolices SET VersaoDosEndossos = v WHERE VersaoDosEndossos = v - 1` + `AplicadoEm` on the endorsement, in one DB transaction (0 rows = already applied). Order is DB, session state, Complete, because neither is transactional with the Complete.
- **Subscribers (Cobrança, Notificação):** one processor class per subscription on `ProcessadorControlavel`; their own `GET /assinaturas` shows filters and pending counts. Logs start with `[assinatura]`.
- **Operations (`Vida.Operacao/Ferramentas`):** `DescobertaDeEntidades` lists queues, topics and subscriptions (with counts and `forwardTo`) on every call; no squad contract referenced. `GET /filas`, `GET /filas/{nome}/mensagens?dlq=`, `POST /filas/{nome}/dlq/reprocessar?removerPropriedade=`, `GET /assinaturas`, `GET /assinaturas/regras`, `GET /assinaturas/{nome}/mensagens?dlq=`, `GET /namespace`. Peek shows Subject, properties and the start of the body as text; it refuses a subscription with `forwardTo` (the broker allows no receiver on a forward source) and a session queue, explaining why. `ReprocessamentoDaDlq` skips permanent reasons and only takes messages up to the DLQ's max `SequenceNumber` peeked at the start; it sends the copy before completing the DLQ message (duplicates rather than loses). A failed forward lands in the source's transfer DLQ (`.../$Transfer/$DeadLetterQueue`), not in the destination's DLQ.
- **Adding a service:** an entry in the `$apps` array of `iniciar.ps1` and in `.vscode/launch.json` (both configurations and the "Fluxo completo" compound), plus a `requests/<squad>/` file.
- **Infra (`infra/main.bicep` → `infra/servicos/`):** `plataforma.bicep` (namespace, RBAC, App Insights); `<servico>.publica.bicep` creates the topics/queues the service owns and outputs their names; `<servico>.assina.bicep` receives those names as parameters (which orders the deploy and breaks the Propostas ↔ Subscrição cycle) and creates its subscriptions; `padroes.bicep` exports `propriedadesDeAssinatura(lockDuration)`. `up.ps1` parameters and outputs did not change.

### Tests

Per squad: `tests/Plataforma/Vida.Plataforma.Testes` (Operação tools), `tests/Propostas/Vida.Propostas.Testes` (API contracts, outbox message, the published contract, strict reading), `tests/Propostas/Vida.Propostas.Testes.Integracao` (`FabricaDaApi` = Propostas in memory + Testcontainers SQL Server, dispatcher and outcome processor removed from the host; `ServiceBusFalso` subclasses `ServiceBusClient`/`ServiceBusSender`; `Banco` collection, sequential), `tests/Subscricao/Vida.Subscricao.Testes` (pricing, review policy, endorsement decision, transient-failure classification, its contract), `tests/Subscricao/Vida.Subscricao.Testes.Integracao` (`RegistroDaAnalise` and `RegistroDeEndossos` against Testcontainers SQL Server: inbox, redelivery, rejection; sequential versions, idempotency key, `SessionId` in the outbox, idempotent apply). Extract decisions out of handlers (like `DecisaoDeEndosso`, `RegistroDaAnalise`) to test them. Pass `TestContext.Current.CancellationToken` to async calls (xUnit1051).

## Working with the user

- Talk to the user in Portuguese. They read the code closely, ask concept questions as they go, and add XML doc comments themselves. Keep their edits.
- Commit only when asked, directly on `master`, with no branches. Before committing, check for and mention the user's own uncommitted edits.
- Infra costs money while it exists. At the end of a session, or after a deploy the user didn't ask to keep, remind them to run `down.ps1`. Check with `az group exists -n rg-servicebus-poc`.
- The `!` prompt prefix runs **bash**, which eats backslashes. Suggest `! pwsh -File infra/up.ps1` (or `down.ps1`, `-ModoDebug`), not `.\infra\up.ps1`.
- Before writing Service Bus facts into docs (limits, semantics), verify them with the Azure MCP `documentation` tool. One claim about multiple matching rules was wrong until checked.

## Conventions for new phases

- Follow the Azure best-practice choices already made: managed identity/RBAC instead of keys, one `ServiceBusClient` singleton per app, infrastructure in Bicep rather than portal clicks, latest stable SDKs (`Azure.Messaging.ServiceBus`, `Azure.Identity`).
- Keep cost in mind: stay on the Standard tier (Premium is ~US$0.93/h). For anything stateful that isn't Service Bus, such as SQL Server for the outbox, run it locally in Docker (`infra/sql-up.ps1`), one database per service.
- A change to a shared library or contract is a new package version (bump `<Version>`, `publicar-pacotes.ps1`), not an edit consumers pick up silently.
- When finishing a phase, update the status table in `README.md` and update `docs/como-funciona.md` in place (don't add per-phase notes): the user wants one document, diagrams over prose. Validate Mermaid blocks parse before finishing. When the user asks a concept question during code reading, they may want the answer saved in `docs/como-funciona.md` too.
